# 项目维护约束与多 Agent 协作规范 v2（步进量化版）

**相对 v1 的变化**：
1. 提交粒度对齐步进式微循环——**一步一提交**
2. 变更日志新增 `step` 段，承载单步声明与自评结果
3. 全部门禁量化，取消无法判定的表述
4. 新增步骤台账与质量指标，防自评虚高

**配套文件**：《方案流程框架 v2》定义做什么；《模块 Loop 执行规范 v2》定义每步怎么做。三份同时生效，冲突时以本文件的**禁止性条款**优先。

# 第 0 部分 · 三条根本原则

## 原则一：仓库是唯一事实来源，不是任何 Agent 的上下文

项目要跑到 2027 年，会经历多个 Agent、多次交接。

> **任何未写入仓库的知识，视为不存在。**

包括：为什么选这条路线、哪些方案试过失败了、某个魔数怎么定的、下一步打算做什么。只存在于会话里的等同于没做过。

## 原则二：数据永不入库

> **真实数据、真实数据的派生统计量、真实客户标识、凭证密钥，一律禁止提交。**

合成数据同样不提交——提交**生成器 + 配置 + 种子**。

**边界特别提示**：本项目里"从真实数据算出的分箱边界、IV 排名、特征分布统计"属**受限产物**，因为它们可能泄露分布信息（M4 不变式 I2）。普通 ML 项目可随便提交，这里不行。

## 原则三：说的和做的必须可机器核验

> **每个涉及跨境信息流的组件必须声明它触碰了哪些跨境资产，CI 自动比对 M0 清单。**

不一致即阻断合并。把合规从"最后写文档"变成"每次提交都在核验"。

# 第 1 部分 · 仓库与目录规范

## 1.1 仓库设置（硬性）

> **v2.1 修订（2026-08-29，依据 `registry/decision_records/DR-GOV-002.yaml`）**：可见性一条按**仓库归属**区分组织/团队仓库与个人仓库；其余条款不变。原文「Private，不得转 public」保留在下表的组织/团队仓库分支中。

| 项 | 要求 |
|---|---|
| 可见性 | **组织/团队仓库：Private，不得转 public**；**个人仓库：可 Public**，但须四项前提全部成立（见下方「个人仓库走 Public 的四项前提」），任一前提不成立即刻转 Private |
| 分支保护 | `main` 禁止直推，必须经 PR |
| 必需检查 | CI 全部门禁通过方可合并 |
| 审查要求 | ≥1 approve；涉及 M0/M9 需合规角色 approve |
| force push | `main` 与 `release/*` 禁用 |
| Secret 扫描 | 开启，含 push protection |
| 历史 | 禁止 rebase 已合并到 main 的历史 |

**个人仓库走 Public 的四项前提（缺一不可）**

1. 仓库归属为**个人账户**，不承载任何机构主体的数据处理活动；不出现机构内部系统名、内部代号、内部端点与未公开的机构材料
   （仓库名中出现机构名作为课题标识不构成违反，但不得据此暗示本仓库是该机构的官方产出）
2. **永不含**真实数据、真实数据派生产物、真实客户标识 —— 第 2 部分本就如此要求，Public 下升级为不可豁免
3. **L-受限产物一律按 L-禁止处理**，取消 2.2 的个案审查放行通道（宁可少提交，不做边界判断）
4. 不含机构内部端点、凭证密钥；门禁 1（数据合规扫描）在每次 push 与 PR 上生效

任一前提不再成立——首次需要提交 L-受限产物、接入真实业务数据或其派生统计量、仓库转交机构主体、需求方或合规角色提出要求——**立即转 Private 并写 DR**。

判定依据是仓库归属与内容，不是"感觉安全"：个人仓库承载了机构数据处理活动时，仍按组织仓库处理。

# 第 2 部分 · 数据与产物分级

## 2.1 四级分级表

| 级别 | 类型 | 处理 |
|---|---|---|
| **L-禁止** | 真实客户数据（任何形式、任何抽样比例）· 真实客户标识（含哈希后）· 凭证密钥 token · 内部端点与真实机构内部命名 · 未审查的真实数据派生统计量 | **绝不提交**，误提交按 2.4 |
| **L-受限** | 真实数据算出的分箱边界、IV/WOE 表、特征分布统计 · 真实样本量与正样本率 · PSI 交集规模 · 模型权重 | **审查后提交**，审查记录写入 changelog；不确定时按 L-禁止 |
| **L-允许** | 合成数据的统计与结果 · 指标表 · 图表 · 脱敏实验日志 · 小体积中间产物（<10MB） | 直接提交 |
| **L-必须** | 全部代码与配置 · 生成器+配置+种子 · 分支卡 · DR · 变更日志 · 组件 schema 与声明 · 文档 | **必须提交**，缺失即视为工作未完成 |

## 2.2 L-受限审查清单（任一命中即降为 L-禁止）

- [ ] 该统计量能否反推个体？（分组过细、极端值暴露）
- [ ] 是否有分组样本量低于 k？（k 取 M0 定义的匿名参数）
- [ ] 是否泄露两侧交集规模或其变化？
- [ ] 是否含真实业务绝对量级（客户数、金额、转化率）？
- [ ] 若被外部看到，是否构成商业敏感信息泄露？

审查结论写入 changelog 的 `sensitive_review` 字段。

## 2.3 大文件与不提交项

- **合成数据不提交**：提交生成器 + config + seed，任何人可重建
- **模型权重默认不提交**：需留存的走 Release 附件或对象存储，仓库内只存哈希与获取方式
- **禁止用 Git LFS 存放任何含数据的文件**——LFS 解决体积问题，不解决合规问题
- 单文件 >10MB 警告，>50MB 阻断

## 2.4 误提交应急流程（发现即执行）

1. **立即**停止该分支后续推送，通知全部参与方
2. 判定级别：L-禁止 → 完整清除；L-受限 → 评估后决定
3. 若已推远端：**先轮换所有可能暴露的凭证**（比清历史更紧急）
4. 用历史重写工具彻底清除，强推（临时解除保护，事后立即恢复）
5. 写 DR：什么泄露、暴露多久、采取何措施、如何防复发
6. 若涉真实个人信息，按 M9 事件响应流程上报

**不要试图用新提交"覆盖"——git 历史里它还在。**

# 第 3 部分 · 提交粒度与步骤台账（v2 核心变化）

## 3.1 一步一提交

**提交粒度严格对齐步进式微循环：一个步骤 = 一次提交 = 一条变更日志。**

| 情形 | 处理 |
|---|---|
| 一步产出多个文件 | 仍是一次提交，文件数不设上限 |
| 一步需要多次修正 | 修正在本地完成，最终**一次**提交；修正轮次记入日志 |
| 想把两步合并提交 | **禁止**。步骤边界即提交边界 |
| 一步做不完 | 拆分后重新声明。拆不拆是判断题，不是算术题 |

**理由**：提交历史与步骤台账一一对应后，任何一步的产出都能被独立回滚、独立复核、独立追责。这是"每步交付物都达标"的物理保证。

## 3.2 单步规模（2026-08-30 修订：取消全部硬上限）

> **本节原为「单步规模上限（CI 检查）」，规定 ≤3 文件 / ≤300 行 / ≤1 路线 / ≤1 结论，超限阻断。
> 现依 `registry/decision_records/DR-GOV-003.yaml` 整体取消——实践中它在三个步骤里触发了两次
> 「例外说明」，把本该完整交付的一步切成互相矛盾的中间态，代价大于收益。**

**现行规则：单步规模不设硬上限，也不设 CI 阻断。** `changelog` 的 `scope` 段继续填写实际规模
（`files_changed` / `lines_added` / `routes_covered`），但它是**记录**，不是**判据**——
用于事后看步子分布，不用于放行。

拆分与否由一条判断题决定：**这一步能否被独立自评、独立回滚、独立追责？**
能就是一步，不论它是 1 个文件还是 60 个文件。不能就拆——典型信号是自评时有多项无法判定
（见《Loop 执行规范》1.2 拆分判据）。

真正不变的边界只剩一条：**一次提交只承载一个步骤**，因为提交历史与步骤台账要一一对应。

## 3.3 步骤台账

每模块维护 `modules/mX/step_ledger.yaml`：

```yaml
module: M5
total_steps_planned: 12          # 对齐框架 v2 的步数预算
steps:
  - step_id: S5.1
    status: committed            # declared | in_progress | committed | escalated | abandoned
    score: 11                    # 自评总分（满分 12）
    gates: {G1: pass, G2: pass, G3: pass, G4: pass}
    dimensions: {D1: 3, D2: 3, D3: 2, D4: 3}
    revisions: 0
    committed_at: 2026-08-28T10:00:00+08:00
    change_id: CL-20260828-M5-001
    commit_sha: 
  - step_id: S5.2
    status: escalated
    score: 8
    revisions: 2
    blocker: "k 值选择缺少业务输入"
current_step: S5.3
metrics:
  avg_score: 10.5                # <10 触发流程复审
  escalation_count: 1            # ≥3 触发模块整体复审
  revision_rate: 0.17            # >0.4 说明步骤划分过粗
  steps_used: 2
  budget_usage: 0.17             # >1.5 触发全局复审
```

## 3.4 台账质量门槛

| 指标 | 门槛 | 触发动作 |
|---|---|---|
| 平均自评分 | <10 | 复审步骤划分与执行质量 |
| 升级次数 | ≥3 | 该模块整体复审是否假设有误 |
| 修正率 | >0.4 | 步骤划分过粗，重新拆分 |
| 步数使用率 | >1.5 | 全局复审 |
| 连续 D4 ≤1 步数 | ≥2 | 强制暂停，重审是否原地打转 |

## 3.5 回溯抽查（防自评虚高）

- 每完成 **5 步**，随机抽 **1 步**由另一 Agent 或人工重新评分
- 复评与自评差 **≥3 分** → 该模块后续所有步骤通过线上调至 **11 分**
- 抽查记录写入 `modules/mX/audit_log.yaml`
- 下游模块发现上游某步产出不可用 → 该步自评作废，回溯修复，记入模块质量记录

# 第 4 部分 · 变更日志规范

## 4.1 changeset 而非单一 CHANGELOG.md

多 Agent 并发改同一个 `CHANGELOG.md` 必然冲突且易丢条目。**每次变更写独立文件到 `changelog/`，CI 聚合生成 `CHANGELOG.md`（禁止手工编辑）。**

命名：`changelog/CL-<YYYYMMDD>-<模块>-<三位序号>.yaml`。跨模块用 `MX`，平台层用 `PLAT`，治理层用 `GOV`。

## 4.2 条目 Schema（v2，新增 step 段）

```yaml

timestamp: 2026-08-28T14:32:00+08:00
agent: <Agent 标识或人名>
module: M5
type: feat | fix | exp | refactor | doc | decision | revert | chore
title: 一行说清改了什么（≤60 字）

# ===== v2 新增：步骤段 =====

  step_id: S5.4
  step_name: L0 与 L1 结果对比
  declaration: |
    执行前的声明原文（will_produce / will_not_produce / success_criteria）
  scope:                      # 记录实际规模，不设上限，不作放行判据
    files_changed: 2
    lines_added: 180
    routes_covered: 1
  gates:
    G1_data_compliance: pass
    G2_cross_border: pass
    G3_scope: pass
    G4_redline: pass
  assessment:

    D2_verifiability: 3
    D3_reproducibility: 2
    D4_information_gain: 3

      D3: "配置已提交，但未实测重跑，故 2 分"

  revisions: 0
  verdict: committed
  next_step: S5.5
# ==========================

  具体改动内容。

  为什么改。实验类须写清验证的假设。
  禁止"优化""改进"这类无信息量表述。

  branch_card: M5-L1-v1

# ===== 本项目特有字段 =====

  若非 none，说明涉及哪些资产、如何变化、依据 M0 清单哪一条。

downstream_affected: [M6, M7]
breaking_change: true | false
migration: |

reproducibility:
  config: modules/m5/configs/l1_v1.yaml
  config_hash: sha256:...
  seeds: [11, 22, 33, 44, 55]
  env_lock: environments/m5.lock

  一句话说清如何回滚。
```

## 4.3 变更类型

| type | 用于 | 需分支卡 | 需 step 段 |
|---|---|---|---|
| `feat` | 新增能力/组件 | 否 | 是 |
| `fix` | 修复缺陷 | 否 | 是 |
| `exp` | 实验路线实现与运行 | **是** | 是 |
| `refactor` | 不改行为的重构 | 否 | 是 |
| `doc` | 文档变更 | 否 | 可简化 |
| `decision` | 判决并选定路线 | **需 DR** | 是 |
| `revert` | 回退 | 需说明被回退 change_id | 是 |
| `chore` | 依赖/CI/工具链 | 否 | 可简化 |

# 第 5 部分 · 分支、提交与 PR

## 5.1 分支命名

```
<模块>/<路线简称>-<版本>     实验分支，必须对应一张分支卡
  例：m5/l3b-splitnn-v1
<模块>/fix-<简述>           修复
<模块>/doc-<简述>           文档
plat/<简述>  gov/<简述>
```

**实验分支必须在开工时立即创建 draft PR**——这是多 Agent 环境下的**认领机制**，draft PR 存在即表示该路线已被认领。

## 5.2 Commit message

```
<type>(<module>): <一行摘要>

<正文：改了什么、为什么>

Change-Id: CL-20260828-M5-004
Step-Id: S5.4
Step-Score: 11/12
Branch-Card: M5-L1-v1
Cross-Border: none
```

CI 校验五个 trailer：
- `Change-Id` 必须存在且对应真实文件
- `Step-Id` 必填（`doc`/`chore` 除外）
- `Step-Score` 必须 ≥10（或 ≥11，若该模块触发了 3.5 的上调）
- `Branch-Card` 在 `type=exp` 时必填
- `Cross-Border` 必填，值为四枚举之一

**Step-Score <10 的提交会被 CI 拒绝。** 这是"每步交付物达标"的硬保证。

# 第 6 部分 · 多 Agent 协作约束

## 6.1 所有权边界

- 每个 Agent 会话开始时明确认领一个模块（写入 `module_status.yaml`）
- 认领模块内自由改动；模块外**只读**
- `platform/` 与 `registry/` 是共享区，改动需额外谨慎（6.5）

## 6.2 认领机制（无实时通信下的并发控制）

```yaml
# registry/module_status.yaml
M5:
  status: in_progress
  claimed_by: <Agent 标识>
  claimed_at: 2026-08-28T09:00:00+08:00
  expires_at: 2026-08-29T09:00:00+08:00   # 24h，过期自动释放
  current_step: S5.3
  active_branches: [m5/l3b-splitnn-v1]
  blocking_on: []
  open_questions:
    - "L1 的 k 值取多少还没定"
```

- 认领有效期 24 小时，过期未续期即视为释放
- 接手过期模块前先读该模块最近的交接记录与步骤台账
- 同模块内不同路线可由不同 Agent 并行认领（通过 draft PR 区分）
- 发现两 Agent 同做一条路线 → 后开工者停止，改做其他路线

## 6.3 跨模块变更流程

1. **不要直接改**
2. 在目标模块的 `blocking_on` 写入条目，说明需要什么
3. 微小明确的变更（typo、类型标注）可直接提 PR，但需标注"跨模块变更"并通知该模块负责人
4. 涉及输出契约的变更**必须先写 DR**，不得先改后说

## 6.4 会话交接协议（每次会话结束必做）

写入 `docs/03-handoff/HO-<YYYYMMDD>-<Agent>-<模块>.md`：

```markdown
# 交接记录

## 本次会话完成的步骤
| Step-Id | 名称 | 分数 | 修正轮次 | 状态 |
|---|---|---|---|---|

## 当前状态
- 当前步骤: 
- 卡在哪里: 
- 已开未合并的 PR: 

## 我的判断与理由
（下一个 Agent 最需要知道的是"你为什么这么选"，
 不是"你做了什么"——做了什么代码和台账里有）

## 试过但失败的
（负面结果义务。哪怕随手试了一下没成，也写）

## 下一步建议
（按优先级，说清为什么是这个顺序）

## 未解决的问题
```

**这份文件不写，会话不算结束。**

## 6.5 共享区改动额外约束

- 改 `platform/` 或 `registry/` 前必须检查是否有其他模块依赖（搜索引用）
- `platform/` 接口变更一律视为 breaking change
- `cross_border_assets.yaml` 是全项目最敏感文件，改动需：合规 approve + DR + 通知全部活跃 Agent

## 6.6 接口契约冻结

模块输出契约一经下游开始消费即冻结。后续变更须走 breaking change 流程 + 提供迁移说明 + 保留旧接口 ≥1 个模块周期。

# 第 7 部分 · 可追溯性与合规核验

## 7.1 组件级跨境资产声明

```yaml
# modules/m5/components/splitnn/declaration.yaml
component: m5.splitnn
version: 0.3.1

cross_border_assets:
  - asset: encrypted_gradient
    direction: cn -> hk
    m0_registry_ref: CBA-006        # 必须指向 M0 清单真实条目
    frequency: per_batch
    volume_estimate: ~2MB/batch
    protection: [homomorphic_encryption, gradient_clipping]
    legal_basis_ref: M0-route-B

audit_hooks:
  - platform.governance.audit.log_cross_border_call

consent_dependency:
  requires_batch: cn_marketing_consent_v2
  revocation_handling: next_batch_exclusion
```

## 7.2 CI 一致性核验（六项，原则三的载体）

1. **引用完整性**：每个 `m0_registry_ref` 在 `cross_border_assets.yaml` 中存在
2. **定性一致性**：声明的 asset 类型与 M0 清单该条目定性一致
3. **路径合法性**：`legal_basis_ref` 指向 M0 选定的主线或回退线，不得引用被否决路线
4. **无未声明流动**：代码有跨方通信调用但组件无对应声明 → 阻断
5. **审计钩子存在**：声明了跨境资产但未挂审计钩子 → 阻断
6. **同意依赖闭环**：`requires_batch` 在同意管理配置中存在

**任一失败即阻断合并。** 到 M9 时几乎不会有惊喜。

## 7.3 审计链

跨境调用运行时记录 9 字段（由 `platform/governance` 统一处理）：
`时间戳 · 批次ID · 组件版本 · 资产类型 · 方向 · 数据量 · 依据的同意批次 · M0 清单条目 · 调用结果`

审计日志不进 git（运行时产物），但**日志 schema 与写入代码必须在 git 里**且有测试保证格式正确。

## 7.4 废弃流程

不允许直接删除组件。三步：标记 `deprecated` 并说明替代方案与移除计划 → 保留 ≥1 个模块周期 → 移除时写 DR 说明确认无引用的方式。

已归档的分支卡与 DR **永不删除**。

# 第 9 部分 · 可复现性约束

1. **配置驱动**：所有实验参数在配置文件中，硬编码魔数 = 0（CI 检查）
2. **种子固定**：种子在配置中声明，禁止代码内硬编码或用系统时间
3. **环境锁定**：依赖版本锁定，环境可重建
4. **配置指纹**：每次实验记录 config hash，结果文件中包含该 hash
5. **结果可追溯**：任何结果表/图能回答"哪个 config、哪些种子、哪个代码版本"
6. **复现验证**：同配置重跑，确定性结果偏差 <1e-6，随机性结果落在 CI 内

**判定标准**：另一个 Agent 在干净环境下只拿仓库和配置，能否复现？不能就是没完成。

# 第 12 部分 · 禁止事项汇总

违反任一项，对应工作作废并需写 DR 说明。

**数据类**
1. 提交真实数据、真实标识、凭证密钥
2. 提交未经审查的 L-受限产物
3. 用新提交"覆盖"误提交的敏感文件而不清理历史

**步进类（v2 新增）**

4. 一次提交跨越两个步骤
5. 未写步骤声明就开始执行
6. 自评无证据引用
7. Step-Score <10 强行提交
8. 修正超过 2 轮仍不升级上报
9. 事后合并已完成的步骤以掩盖低分

**追溯类**

10. 提交无 `Change-Id` 或无 `Step-Id` 的 commit
11. 删除失败分支卡或已归档 DR
12. 手工编辑 `CHANGELOG.md`
13. 把知识只留在会话上下文而不写入仓库

**合规类**

14. 引入未在 M0 清单登记的跨境资产
15. 组件有跨方通信但无声明或无审计钩子
16. 通过修改文档消除"说做不一致"（必须改实现）
17. 自审 `cross_border_assets.yaml` 的改动

**协作类**

18. 未认领即改动他人模块
19. 未走 DR 直接变更已被消费的输出契约
20. 会话结束不写交接记录
21. 重复开工已有 draft PR 的路线

**科学性类**

22. 测试集上做分支选择
23. 实验后修改指标定义或评估口径
24. 用单种子、无 CI 的结果下结论
25. 隐瞒失败分支或负面结果
