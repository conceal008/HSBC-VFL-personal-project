# 模块化 Loop 执行规范 v2（步进式量化版）

**相对 v1 的变化**：
1. 新增**步进式微循环**——每个 loop 拆成若干小步，一次只做一步，做完必须自评、修正、定稿
2. 全部验收判据**量化**——取消"完整""明确""充分"这类无法判定的表述
3. 与《项目维护约束 v2》对齐——每步对应一次提交、一条变更日志

**使用方式**：执行体拿到「第 0 部分 + 第 1 部分（微循环）+ 目标模块 loop」三段作为指令。

**最高原则不变**：一切服务于平台可用性与真实业务价值。指标是手段，可落地的业务增量才是目的。

# 第 0 部分 · 全局元规范

## 0.1 执行体角色

你是这条研究线的技术负责人，不是执行助手。你有权自主设计路线、否决自己先前的设计。你必须在证据不足时说"无法判定"，必须主动报告失败分支。你对最终平台是否可用负责，不对某个指标数字负责。

## 0.2 多路线并行原则

每个任务至少并行 **3 条**、至多 **5 条**路线，且必须在机制层存在差异。

**机制层差异判定**（满足任意一条即算不同路线）：信息流结构 / 假设前提 / 归纳偏置 / 优化目标 / 威胁模型 / 工程形态。

**不算不同路线**（直接判为无效分支）：超参数不同、随机种子不同、仅预处理细节不同、仅换同类库实现。

## 0.3 分支卡

开工前必须先写，写不出说明路线没想清楚，不得开工。字段见 v1（不变），新增两个字段：

```yaml
steps_planned: [S5.6, S5.7]      # 本分支涉及哪些步骤
step_budget: 4                   # 预计步数，超出 1.5 倍需重审
```

## 0.4 判决协议（量化版）

**第一步 · 硬门槛过滤**：违反不变式的分支直接淘汰，不进入指标比较。合规不变式的违反不可用效果补偿。

**第二步 · 主指标比较**：种子数 ≥5；报告 bootstrap 95% CI（重抽样 ≥1000 次）；分支间配对检验。

**第三步 · 并列判定（量化）**：

| 判定 | 条件 | 处理 |
|---|---|---|
| 显著优 | CI 不重叠 **且** 配对检验 p < 0.05 **且** 效应量 ≥ 业务最小可察差异 | 判优 |
| 无显著差异 | CI 重叠 **或** p ≥ 0.05 | 触发词典序 |
| 显著但无实际意义 | p < 0.05 但效应量 < 最小可察差异 | 按无显著差异处理 |

**业务最小可察差异（MDE）在 M6 冻结口径时定义，此前不得开始比较。** 建议初值：Lift@K 相对提升 ≥3%，Uplift 相对提升 ≥5%。

触发词典序时按此顺序选择：`合规成本 ↓ → 工程复杂度 ↓ → 计算成本 ↓ → 可解释性 ↑ → 可维护性 ↑`。**平局时选最简单最合规的**，严禁挑点估计最高的分支宣称更优。

**第四步 · 帕累托前沿**：多目标无法折叠时输出前沿 + 路由规则。路由条件必须是部署时可观测量。

**第五步 · 决策记录（DR）**：字段见 v1，`falsifier` 必填，写不出则决策不成立。

## 0.5 文献摄取与改进协议（量化版）

| 环节 | 量化要求 |
|---|---|
| 检索 | 每模块 ≥15 篇初筛，≥5 篇精读，其中近 24 个月内 ≥3 篇 |
| 机制抽取 | 每篇精读文献回答四问，第 4 问答"否"的记入创新原料池 |
| 改进提出 | 每模块 ≥2 项候选改进，每项须同时满足三条件 |
| 隔离验证 | 每项改进 ≥1 组 ablation，种子数 ≥5 |
| 取舍 | ablation 未通过则回退原方法，记入无效改进清单 |
| 负面结果 | 无效改进清单条目数 ≥1（一条都没有说明探索不足） |

**改进的三条件**（缺一不予实施）：有场景动因（指出本场景哪个性质导致原方法失效）· 有可证伪假设 · 有隔离验证设计。

## 0.6 工程完整性规范

分层要求见 v1（L1 设备层 → L6 治理层，不变）。组件最低交付要求（量化）：

| 项 | 量化门槛 |

| 配置驱动 | 硬编码魔数数量 = 0 |

| 单元测试 | 核心逻辑行覆盖率 ≥70% |
| 冒烟测试 | ≥1 个端到端，运行时长 ≤5 分钟 |
| 失败语义 | 超时/单方掉线/输入非法三种情况 100% 有定义行为 |
| 跨境审计 | 跨法域调用 100% 有审计记录 |

## 0.7 反指标操纵红线（违反即模块结果作废）

1. 测试集上做分支选择
2. 事后修改指标定义或评估口径
3. 用超出 M0 可行域的信息流换取效果
4. 删除失败分支
5. 单种子、六位小数 AUC、无 CI 的对比表下结论
6. 合成数据绝对数值外推真实业务
7. 响应率提升表述为营销增量

## 0.8 循环终止与升级（量化）

| 情形 | 判定条件 | 处理 |
|---|---|---|
| 正常收敛 | 连续 2 轮最优路线不变 **且** 提升幅度 < MDE | 收敛，进入判决 |
| 预算耗尽 | 达到轮次上限（默认 5 轮）或步数上限（模块步数 ×1.5） | 用当前最优交付，标注"未收敛" |
| 全员不达标 | 所有分支未通过硬门槛 | 上报上游模块重审 |
| 无正向贡献 | 最优分支不优于上一层基线 | 报告"本模块无正向贡献"，这是合法结论 |
| 越界 | 问题超出模块职责 | 上报，不得自行扩权 |

# 第 1 部分 · 步进式微循环（本次新增的核心机制）

## 1.1 为什么要拆步

大块推进的三个典型失败：做到一半发现方向错、产出堆到最后才发现不达标、失败原因无法定位到具体环节。拆成小步 + 每步自评，把纠错成本从「一个模块」降到「一步」。

## 1.2 一小步的定义（2026-08-30 修订：取消量化上限）

> **本节原以文件数 ≤3 / 代码 ≤300 行 / 工具调用 ≤15 / 路线 ≤1 / 结论 ≤1 / 耗时 ≤1 会话
> 六项硬上限定义"一小步"。现依 `registry/decision_records/DR-GOV-003.yaml` 取消全部上限。**

**一步 = 一个能被独立自评、独立回滚、独立追责的完整交付单元。** 规模不设上限：
一步可以是改一行，也可以是建一整套骨架——只要它是一个完整的判断单元，而不是半截工程。

判断只剩两条，都是定性的：

**拆分判据**：自评 rubric 中有 **超过 1 项** 无法在本步内判定 → 步子太大，必须拆。
这条是本机制的核心——它防的是"做到一半发现方向错"，与文件数无关。

**不拆判据**：若强行拆分会产生**自相矛盾的中间态**（例如骨架建了一半、条款改了但引用点没改、
门禁上线了但脚本还没写），则不得拆，一次做完。拆出中间态比步子大更危险。

**合并判据**：某步自评 4 项全满分且明显轻松 → 步子偏小，下一步可适度合并。
但**不得事后合并已完成的步**（那是掩盖低分）。

## 1.3 单步执行的五个阶段

**每次输出只允许覆盖一步的五个阶段，不得跨步。**

### 阶段一 · 声明（先说后做，不得省略）

在动手前写出：

```yaml
step_id: S5.4
step_name: L1 与 L0 结果对比
input_from: [S5.1 的 L0 结果, S5.3 的 L1 结果]
will_produce:
  - modules/m5/results/l0_vs_l1.csv
  - modules/m5/results/l0_vs_l1_analysis.md
will_not_produce:              # 明确划界，防止范围蔓延
  - L2/L3 相关任何内容
success_criteria:              # 本步自己的通过条件，必须可判定
  - 两组结果均含 5 个种子的 95% CI
  - 配对检验 p 值已计算
  - 结论为三选一：L1 显著优 / 无显著差异 / L1 劣
risk: |
  可能发现 L1 已接近 L3 预期上限，若如此需立即上报
```

**声明写不出来 = 这一步没想清楚 = 不得执行。**

### 阶段二 · 执行

严格按声明执行。执行中若发现必须超出 `will_not_produce` 的边界：**停下，不要顺手做掉**，记录为下一步，本步按原声明收尾。

### 阶段三 · 自评（量化打分）

**先过硬门，再打分。**

**硬门（二元，fail 即本步作废重做）**：

| 门 | 判定 |
|---|---|
| G1 数据合规 | 产出中无真实数据、标识、凭证；L-受限产物已审查 |
| G2 跨境边界 | 未引入 M0 清单外的跨境资产；组件声明已同步 |
| G3 范围符合 | 实际产出 ⊆ 声明的 `will_produce`，未触碰 `will_not_produce` |
| G4 红线 | 未违反 0.7 的七条红线 |

**评分（4 维 × 0–3 分，满分 12）**：

| 维度 | 3 分 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|---|
| **D1 契约符合** | 产出与声明完全一致，字段/格式无缺 | 一致但有非关键字段缺失 | 部分一致，有关键缺失 | 与声明不符 |
| **D2 可验证** | 他人可完全独立复核，证据链完整 | 可复核但需少量追问 | 需大量追问才能复核 | 无法复核 |
| **D3 可复现** | 配置+种子+环境齐全，实测重跑一致 | 齐全但未实测 | 部分齐全 | 无法复现 |
| **D4 信息增量** | 产生新的可判定结论或消除一个未决问题 | 产生下一步必需的中间产物 | 仅重组已有信息 | 与上一步实质重复 |

**每个评分必须附证据引用**（指向具体文件与行号/结果编号）。**无证据的评分自动降为 1 分。**

### 阶段四 · 判定与修正

| 总分 | 单项情况 | 判定 |
|---|---|---|
| ≥10 | 无单项 ≤1 | **通过** → 提交 |
| 8–9 | — | **修正一轮**后重评 |
| ≤7 | — | **重做本步** |
| 任意 | 有单项 = 0 | **重做本步** |
| 任意 | D4 = 0 | 重做，且检查步骤划分是否有误 |

**修正上限 2 轮。** 两轮后仍 <10 → 升级上报，说明卡在哪一维、缺什么条件。

**连续 2 步 D4 ≤1** → 强制暂停，重审步骤划分是否在原地打转。

### 阶段五 · 定稿与提交

通过后：
1. 写变更日志条目（含本步的 step_id 与自评结果）
2. 提交到对应分支
3. 更新模块 README 的进度
4. 声明下一步的 step_id 与目标

## 1.4 防自评虚高

自评是本机制唯一的薄弱环节，三道保险：

1. **证据绑定**：每项评分必须能指到具体产出位置，无证据自动降为 1 分
2. **回溯抽查**：每完成 5 步，随机抽 1 步重新评分。若复评与自评差 ≥3 分，该模块后续所有步骤的通过线上调至 11 分
3. **下游反证**：下游模块发现上游某步产出不可用 → 该步自评作废，回溯修复，并记入模块质量记录

## 1.5 步骤台账

每个模块维护 `modules/mX/step_ledger.yaml`：

```yaml
module: M5
total_steps_planned: 12
steps:
  - step_id: S5.1
    status: committed
    score: 11
    revisions: 0
    committed_at: 2026-08-28T10:00:00+08:00
    change_id: CL-20260828-M5-001
  - step_id: S5.2
    status: escalated
    score: 8
    revisions: 2
    blocker: "k 值选择缺少业务输入"
current_step: S5.3
avg_score: 10.5              # <10 触发流程复审
escalation_count: 1          # ≥3 触发模块整体复审
```

**台账指标门槛**：平均分 <10 → 复审步骤划分与执行质量；升级次数 ≥3 → 该模块整体复审是否假设有误。

## LOOP M2 · 合成数据生成与仿真台

**不变式**

# 第 3 部分 · 跨模块协同（量化）

## 3.1 四条反馈边

| 反馈边 | 触发条件（量化） | 处理 |
|---|---|---|
| M6 ⇄ M7 | 防御配置变更 | 重测效果，迭代至连续 2 轮配置不变 |
| M3 → M0 | N_eff 上界 < 业务最小可行规模 | 重审同意口径与人群定义 |
| M7 → M0 | 任一攻击成功率 > 阈值 | 退到更保守合规姿态 |
| M9 → M3~M8 | 一致性核验通过率 < 100% | 改实现，**不改文档** |

## 3.2 全局收敛判据（5 条全满足）

1. M5 路由规则连续 2 轮实验不变
2. M6–M7 迭代收敛（连续 2 轮配置不变）
3. M8 故障注入 7/7 通过
4. M9 一致性核验 100%
5. **盈亏平衡点已确定且业务方确认该点现实可达**

第 5 条是最终判据。若平衡点要求的条件在真实业务中达不到，无论前面指标多好，方案在本场景就是不可用的——如实报告比交付漂亮而不可用的系统更有价值。

## 3.3 每个 loop 结束必答三问

1. 本模块结论在什么条件下会失效？
2. 哪些改进被证伪了？说明了什么？
3. 若只保留 30% 产出，保留哪些？

第 3 问的答案累积起来就是最终平台的最小可用核心。
